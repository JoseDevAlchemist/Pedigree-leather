# Shared POS and storefront catalogue contract

Audited 2026-11-18 against Pedigree Leather HEAD `94cb683` and its existing working tree, and POS 2.0 (`posversion2`) HEAD `ba53643` and its in-progress working tree. The contract below comes from checked-in schema and storefront consumers. Confirm the deployed migration ledger, grants, bucket settings and cache behaviour in staging. No production requests or database writes were made during this audit.

## Product, category, colour and image rows

| Table | Database contract and POS write requirements |
| --- | --- |
| `public.products` | `id uuid` primary key, generated by default. Use a stable UUID for uploads and the saved product. `name text NOT NULL`, `slug text NOT NULL UNIQUE`, `description text NOT NULL DEFAULT ''`. Supply a meaningful name and description and a unique, stable, lowercase hyphenated slug. `category text NOT NULL` accepts only `bag` or `shoe`. `category_id uuid NULL` references `categories.id` with `ON DELETE SET NULL`. Supply an active category ID for dynamic merchandising. |
| Product pricing and flags | `base_price integer NOT NULL` in whole KES, at least 0. `base_price_usd integer NULL` is a positive whole-USD override. `discount_percent integer NOT NULL DEFAULT 0` has a database range of 0–100. Use 0–99 for storefront interoperability because its form rejects 100 and its price helpers only apply discounts of 1–99. `featured boolean NOT NULL DEFAULT false`, `active boolean NOT NULL DEFAULT true`, `created_at timestamptz NOT NULL DEFAULT now()`. |
| Product publication and SKU | Migration 024 adds `barcode text NULL`, with a partial unique index on non-null codes, and `publish_to_pos` and `is_website_published`, both non-null booleans with default true on a fresh storefront migration chain. The POS catalogue migration specifies default false for `is_website_published` when it adds that column first. Set publication explicitly and store a trimmed SKU or null. Materials, an image array column and `qr_code` are absent from the storefront migration contract. Older POS code may expect `qr_code`. |
| `public.categories` | `id uuid` primary key, `name text NOT NULL`, `slug text NOT NULL UNIQUE`, `parent_id uuid NULL` self-FK with `ON DELETE SET NULL`, `display_order integer NOT NULL DEFAULT 0`, `is_active boolean NOT NULL DEFAULT true`, `created_at timestamptz NOT NULL DEFAULT now()`. Select the applicable active category or direct child of an active parent. Parent grids include their own products and direct children. Preserve the existing category IDs. |
| `public.product_colors` | `id uuid` primary key, `product_id uuid NOT NULL` FK to `products.id` with cascade, `color_name text NOT NULL`, `color_hex text NOT NULL`, `sort_order integer NOT NULL DEFAULT 0`, `stock_quantity integer NOT NULL DEFAULT 1` with nonnegative check after migration 022. Unique `(product_id, color_name)`. Write one or more colour rows with stable IDs, nonempty distinct names, six-digit `#RRGGBB`, explicit stock including zero, and sequential sort order. |
| `public.product_images` | `id uuid` primary key, `color_id uuid NOT NULL` FK to `product_colors.id` with cascade, `angle text NOT NULL` with the eight-value check below, `image_url text NULL`, `sort_order integer NOT NULL DEFAULT 0`. Unique `(color_id, angle)`. Each image belongs to one saved colour. Write one row per actual image, with zero-based order per colour. Empty slots may be omitted. |

The storefront form applies tighter bounds than SQL and the POS create RPC. Keep website-published products editable in both apps by using name 2–80 characters, slug 2–80 characters matching `^[a-z0-9]+(-[a-z0-9]+)*$`, description 1–600, optional SKU at most 128, KES price at most 10,000,000, optional USD override up to 1,000,000, 1–8 colours with names up to 40 and stock 0–100,000. The inspected POS create RPC appends the full UUID to a generated slug and permits longer names and more colours, so these bounds need explicit alignment for shared products. Source: [storefront validation](../lib/validation.ts), [initial catalogue](../supabase/migrations/001_initial.sql), [USD price](../supabase/migrations/010_usd_pricing.sql), [categories](../supabase/migrations/021_categories_reconcile.sql), [colour stock](../supabase/migrations/022_color_stock.sql), [publication and currency](../supabase/migrations/024_product_pos_and_currency.sql).

### Categories, availability and publication

- `category_id` drives `/category/<category-slug>`, dynamic navigation and category discovery. `category` still drives `/bags/<product-slug>` and `/shoes/<product-slug>`, default angles, card links and product URLs in the sitemap. Populate both. The storefront form derives the discriminator from the root category's name/slug using footwear keywords. The POS create RPC checks for an ancestor with slug `shoes`. These agree for the seeded Bags/Shoes tree and can diverge for custom footwear roots. Coordinate an explicit mapping for those roots. Source: [admin form](../components/admin/ProductForm.tsx), [category routes](../lib/category.ts), [catalogue queries](../lib/api.ts), [sitemap](../app/sitemap.ts).
- Set `active=true` and `is_website_published=true` for website publication. Storefront migration 001 grants anonymous reads for active rows. POS 2.0's initial catalogue migration replaces those named public product/colour/image policies with active-and-published checks. Storefront queries currently lack a consistent explicit `is_website_published` filter, and the live anonymous policy is unverified. Do not rely on a false publication flag to hide an active draft until that boundary is tested. Public bucket objects remain accessible by URL independently of row publication. `publish_to_pos` is separate. Migration 024's POS restriction depends on `pos_is_staff()` already existing at application time. Source: [catalogue queries](../lib/api.ts), [storage migration](../supabase/migrations/002_storage.sql), [publication migration](../supabase/migrations/024_product_pos_and_currency.sql).
- Storefront product projections use an inner join to colours. Supply at least one readable colour with positive stock for a reachable detail page. With positive stock in any colour, the storefront mapper's read wrapper removes unavailable colours. With zero stock everywhere, catalogue cards can show sold out while both product detail routes return 404 and metadata reports “Not found”. The sitemap uses the catalogue list and can therefore still list a sold-out URL. Stock belongs at `product_colors.stock_quantity`, and colour IDs are referenced by carts and can be referenced by POS records. Keep IDs stable. Source: [catalogue queries](../lib/api.ts), [product card](../components/product/ProductCard.tsx), [bag detail](../app/(shop)/bags/%5Bslug%5D/page.tsx), [shoe detail](../app/(shop)/shoes/%5Bslug%5D/page.tsx).
- The website reads `shop_settings.exchange_rate_kes_to_usd` from `id='default'`, defaults to 130 KES per USD, and displays `base_price / rate` unless the product carries an explicit USD override. The discount applies to both displays. Website checkout remains KES. Keep SKU and POS operational fields out of anonymous catalogue projections. The current public `PRODUCT_SELECT` uses a product wildcard, so it conflicts with the POS private-code migration that revokes direct barcode SELECT. A public response can also select the SKU under broad grants even though the mapper omits it. Coordinate the explicit storefront projection before any grant change. Source: [currency settings](../lib/settings-api.ts), [price formatting](../lib/format.ts), [catalogue queries](../lib/api.ts).

## Angles, storage and rendering

Supported values are `front`, `side-left`, `side-right`, `side`, `top`, `bottom`, `back`, `laces`. Defaults are `front, side-left, side-right, top, back` for bags and `front, laces, side, back, bottom` for shoes. Each colour may use any subset. The mapper walks colours by sort order then name and forms the product-wide union of photographed angles, ordering each colour's contributions by image sort order with category-order tie breaking. A missing angle in another colour shows a placeholder. Give the first available colour a front image and keep preferred angle order consistent across colours. Source: [angle definitions](../lib/angles.ts), [mapper](../lib/mappers.ts).

1. **Local file → Storage.** The storefront form supports batch JPEG/JPG, PNG and WebP, max 4 MiB per file. Its helper also accepts AVIF, converts non-WebP inputs in the browser, rechecks the encoded size, and uploads actual WebP bytes with `Content-Type: image/webp` using the signed-in browser client. It uses `<product-uuid>/<slugified-colour>-<angle>.webp` inside the public `product-images` bucket. Migration 002 sets an 8 MiB bucket cap and accepts JPEG, PNG, WebP and AVIF. The POS snapshot uses a manager-guarded server action, preserves source bytes and MIME, uses versioned object names, and enforces 4 MiB per file. A JPG with matching bytes/MIME is compatible. Use one upload per server-action request under the POS 5 MB request limit. Source: [admin form](../components/admin/ProductForm.tsx), [upload helper](../lib/upload.ts), [bucket migration](../supabase/migrations/002_storage.sql).
2. **Storage → image rows.** Persist an absolute public object URL of the form `https://<shared-storage-host>/storage/v1/object/public/product-images/<encoded-object-key>`, preferably from the Storage SDK. Generate ASCII keys or encode path segments once. Unencoded `#` and `?` become fragment/query delimiters. Keep the configured browser-reachable shared origin, including in local testing. The resolver keeps the origin embedded in absolute URLs, including URLs from a different project or a loopback origin. Use a new key or `?v=<version>` on replacement. Preserve historic keys. Avoid POS-only relative paths, blob/data previews, expiring signed URLs and hand-built render URLs in persisted image rows. A path beginning with `/` resolves against the storefront domain when rendered there.
3. **Rows → mapper → UI.** The storefront reads `products → product_colors → product_images`. The mapper preserves the source URL, drops unknown angles, and treats empty URLs as unphotographed. Cards and detail galleries use `ProductImage`. Admin form previews use the temporary blob or stored URL with `unoptimized`, so they request the original. Missing or failed storefront photos use a colour placeholder. The error handler shows the placeholder if the original fails to load. A valid Storage object with no associated image row, the wrong colour ID or a missing angle can therefore produce the same visual placeholder as a network error. Source: [mapper](../lib/mappers.ts), [product image](../components/product/ProductImage.tsx), [admin form](../components/admin/ProductForm.tsx).
4. **Browser request.** Next.js uses `images.unoptimized` and the browser requests original public Storage objects directly. The storefront URL resolver converts legacy transform URLs to the object path at display time and preserves the host, encoded path and query. Grid images are lazy and detail pages load only the selected angle. Existing WebP, JPG and PNG files are served as stored. [URL resolver](../lib/product-image-url.ts), [Next config](../next.config.ts).

### Diagnosis

- The reported production 403 affected the historical transform endpoint. The Free-plan fix removes that dependency. Local checks cover direct URL output and the fallback. Live object responses and browser rendering still need staging verification.
- Both detail routes now use the stored front image through the same URL resolver for Open Graph and Twitter. The earlier doubled-host URL construction was removed. [Bag detail](../app/(shop)/bags/%5Bslug%5D/page.tsx), [shoe detail](../app/(shop)/shoes/%5Bslug%5D/page.tsx).
- **Confirmed POS write gap in the inspected snapshot.** The create form and latest create RPC accept a single `imageUrl` per colour and write `front` only. The edit path accepts angle arrays, but the current update RPC inserts each image with `sort_order=0` and does not update `category_id`. The existing editor can also accept relative URLs. These conditions explain missing views, fallback order or stale category links independently of Storage or WebP. POS source locations are `components/manager/product-create-form.tsx`, `lib/products/actions.ts`, `lib/validation/products.ts` and migrations `20261118100000_pos_manager_settings_catalogue.sql` and `20261117120000_pos_product_publishing.sql`.

## Visibility after writes and proposed ownership

Storefront product actions invalidate the home page, legacy grids, dynamic category and detail pages, and sitemap. Category actions also invalidate the storefront layout. Detail routes use `generateStaticParams` and can resolve new slugs on demand. POS actions invalidate their own manager/till routes. There is no reviewed cross-deployment invalidation signal. A first request to a new URL can behave differently from a warmed homepage, detail URL, category or sitemap. Database visibility and browser/CDN image caching are separate from Next route caching. Source: [product actions](../lib/actions/products.ts), [category actions](../lib/actions/categories.ts), [sitemap](../app/sitemap.ts).

| Owner | Proposed minimal follow-up |
| --- | --- |
| POS 2.0 | Pass ordered image arrays in create and edit, persist each angle against its saved colour ID with sequential order, and validate shared public object URLs for website publication. Preserve stable colour IDs and existing stock/history. Save the active category ID and the agreed legacy type together. Align shared field limits so either admin can edit the product. Keep the existing bucket and tables. Any RPC signature or migration change needs joint review. |
| Storefront | Use an explicit anonymous product projection and enforce the website publication predicate when the shared schema is ready. Preserve existing colour IDs when editing POS products in a separate, coordinated change. |
| Both | Agree on publication/RLS and SKU grants, verify the actual schema and compatible migration order, and define how a committed POS catalogue change invalidates storefront pages. A small authenticated storefront revalidation endpoint called after a successful POS save is one option. Define timing and failed-invalidation behaviour before shipping. |

## Staging integration checklist

- [ ] Confirm shared project identity, migration ledger, catalogue constraints and FKs, SKU grants, category rows, publication RLS, exchange-rate row and bucket policy. Confirm anonymous product and nested queries succeed with the intended projection and do not return a SKU.
- [ ] Create a POS draft in an active child category with two colours, distinct stock levels, mixed JPG and WebP files and multiple angles. Verify product, colour and image FKs, MIME, sort order and angle uniqueness. Test duplicate angle, invalid MIME, oversized and empty files, and a missing angle.
- [ ] With the storefront home, search, category, detail and sitemap warmed, verify the draft stays hidden. Publish it and verify discoverability in parent and child categories, the matching bag/shoe route, correct name and images, and the publication-to-visibility interval. Repeat for unpublish and inactive.
- [ ] In admin and storefront Network panels, verify the direct public object URL returns HTTP 200 for WebP and JPG. Check MIME, decodability, encoded keys, versioned replacements, and the image crop in the existing frame. Confirm no product requests use the paid transformation path or the Next.js image optimizer.
- [ ] Verify colour switch, angle order, back/side views, sparse-angle placeholders, mobile and desktop galleries, and the expected placeholder when an original object fails to load. Compare metadata images and canonical product paths, and check sitemap behaviour when all stock reaches zero.
- [ ] Verify SKU search in the till and anonymous SKU exclusion, independent publication toggles, stable colour IDs after editing from both apps, positive-stock purchase controls, sold-out cards and detail 404s, USD override and exchange rate, and unchanged KES checkout pricing.
